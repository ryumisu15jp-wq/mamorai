## 0. エグゼクティブサマリー

- 警備業は「市場は伸びるが担い手が枯れる」構造。売上総額 約3.5兆円・警備員 約58.8万人・**60歳以上が47%**・保安職の有効求人倍率 **6.59倍**（2026年1月）という極端な人手不足下にあり、**シフト最適化と事務省力化のニーズは構造的に強い**。
- 一方で **警備員100人未満の中小が業者の90.2%** を占め、資金力のある大手だけがDX投資できる「テック導入格差」が拡大中。ここに MAMOR-AI の狙う市場（中小警備会社向け低価格帯）がある。
- 競合は「警備特化・ワンストップだが料金非公開／高額」（KUMOCAN・KOMAINU・警備フォース・プロキャス警備）と、「低価格でAI配置最適化まで入っている新興」（クリエイトシステム「警備スマート管理」月額3,980円〜）に二極化。**"AIシフト×低価格"だけでは既に先行者がいる**点は正直に直視すべき。
- MAMOR-AI の勝ち筋は、単機能の安売りではなく **「既存のClaude APIリスク予測エンジン」×「1分日報の軽量入力UX」×「AIシフト最適化」を1つのデスクトップ体験に統合**すること。特に「日報が続く（＝現場データが溜まる）→リスク予測とシフト最適化の精度が上がる」というデータ循環は他社にない差別化軸。

## 1. 対象市場

### 1-1. 市場構造と規模（WebSearch で確認）
- **市場規模**: 令和6年（2024年末）時点で警備業者の売上高総額 **約3兆5,000億円**、認定警備業者 **10,811業者**、警備員総数 **587,848人**。市場は堅調に成長（警備NEXT／警察庁統計ベース）。
- **業種構成**: 警備業法上の1号（施設警備）・2号（交通誘導・雑踏）・3号（貴重品運搬）・4号（身辺警備）。本プロダクトが主対象とするのは **施設警備・交通誘導・巡回** で、いずれも「現場に人を張り付け、日々の記録と勤務割を回す」業務。MAMOR-AI のモックアップ（ブルガリホテル東京等の施設警備を想定）も1号業務が中心。
- **機械警備**: 機械警備対象施設は342万施設超（前年比+5.9%）と伸びるが、これはセコム・ALSOK等の大手領域。中小の主戦場は依然として「人的警備」であり、そこでは勤務管理・日報・シフトが手作業・Excel・電話に依存している。

### 1-2. 中小警備会社のIT化状況・課題（WebSearch で確認）
- **担い手の高齢化**: 警備員の **60歳以上が約47%**（70歳以上が20.9%）、20〜30代は19.4%のみ。→ 管制・現場ともにITリテラシーが高くない前提でUIを設計する必要がある（「高齢者でも迷わない」がCTSYS等の訴求軸になっている）。
- **極端な人手不足**: 保安職業従事者の有効求人倍率は **6.59倍**（2026年1月、全体平均1.18倍の約5倍）。限られた人員を法令・資格・休日制約の中で配置する「シフト最適化」の価値が非常に高い。
- **中小の淘汰と資金力格差**: 業者の **90.2%が警備員100人未満**。倒産・休廃業が高止まりし、東京商工リサーチは「大手は積極投資、中小は資金繰り上IT投資が負担」という**テック導入格差**を指摘。→ 中小が払える価格帯（月数千円〜1万円台）と、導入の心理的ハードルの低さ（無料/安価スタート・要問合せでない明朗価格）が普及の鍵。
- **政策の追い風**: 警察庁が令和7年12月に「省力化投資促進プラン（警備業）」を公表。省力化・DXが業界の公式方針として推進されており、補助金・機運の面で追い風（詳細な補助対象は**要確認**）。

> 市場の要旨: 「伸びる市場 × 深刻な人手不足 × IT化が遅れた中小が多数 × 政策の後押し」。ソフトウェアによる省力化の余地は大きいが、価格感度と低ITリテラシーという制約が同時に存在する。

### 2-1. ユーザーレビュー・現場視点から見た不満点（品質基準）
- 警備特化ワンストップ系（KUMOCAN/KOMAINU/プロキャス等）への典型的不満は **「料金が非公開・個別見積もりで比較しづらい」「初期費用が重い」「機能が多く管制向けで、現場隊員の入力が面倒」**。比較記事でも「複数社を同条件で見積もり必須」と助言されるほど価格の不透明さがネック。
- 汎用勤怠・汎用シフト（AirSHIFT等）は安いが **「警備の上下番・配置基準・資格要件・現場ごとの日報様式に合わない」** ため結局Excel併用になる、という構造的ミスマッチ。
- 現場（隊員）目線では **「日報入力が煩雑・PCでしか書けない・項目が多い」** が離脱要因。MAMOR-AI の「1分日報」はこの不満に直接刺さる。
- ※ 個別アプリのApp Store/Google Playレビュー原文までは今回の調査で未取得（多くが管制向けBtoB Web管理でストア評価が乏しい）。定量的な満足度は **要確認**。

## 3. 機能分類（Must-have / Differentiator / 避けるべき）

### 3-1. Must-have（必須 ─ なければ検討対象に入らない）
- **勤怠・上下番（出退勤）記録**: 警備特化・汎用問わず全競合が実装。GPS打刻/QRコード等、低ITリテラシー層でも押せる導線が前提。
- **シフト表・配置表の作成と共有**: MAMOR-AI の p-shift / p-assign に相当。カレンダー型勤務表と日次配置表は業界標準。
- **日報の作成・一覧・承認フロー**: p-rlist / p-rnew / 承認（提出済→承認済→差し戻し）。監査・請求根拠として必須。
- **月報・集計出力（PDF/Excel）**: p-month。請求・報告のため出力機能は必須。
- **拠点/現場切り替え・複数現場管理**: 中小でも複数現場を持つため必須。

### 3-2. Differentiator（差別化 ─ MAMOR-AI だけの強み）
1. **1分日報の軽量入力UX（最重要差別化・その1）**
   - 競合の日報は項目過多・PC前提で「隊員が書きたがらない」のが共通課題。MAMOR-AI は **最短タップで約1分**の入力フローを核に据える。
   - **技術的実現性は高い**: 前日・テンプレートからのプリフィル、カウンタ/選択式中心（モックの counter/table/check テンプレ型が既にこの思想）、定型文サジェスト。入力ロジックを**UIから分離した共通層**として実装する方針は、将来のExpo（スマホ）展開でそのまま再利用でき、差別化を横展開できる。
2. **リスク予測エンジンとの統合（最重要差別化・その2 ─ 他社に無い独自資産）**
   - 既存の Claude API 予測エンジン（p-risk / ダッシュボードの「MAMOR-AI予測」）は競合に存在しない。**「日報が溜まる→インシデント/誤進入/発報パターンを学習→当日リスクを提示→巡回・配置に反映」**というデータ循環は、単なるシフト表作成ツールにない付加価値。
   - これにより「日報を続ける動機（＝予測が当たる）」が生まれ、1分日報とAIシフトが相互に価値を高める**フライホイール**を構成できる。
3. **中小向け低価格AIシフト最適化（差別化・その3、ただし要注意）**
   - 資格・休日・配置基準・法令制約を扱う警備シフトは、**数理最適化が本質的に向く**問題（制約が明確・多岐）。既存Claude APIは制約理解や自然言語での要望反映に使い、割付は最適化ソルバーで解く**ハイブリッド**が筋。
   - ただし後述の通り「低価格AI配置最適化」は **クリエイトシステム（月3,980円〜）が先行**。価格だけでは差別化にならないため、**MAMOR-AIは「日報→リスク→シフト」の統合体験と、デスクトップでの快適さ**で上回る設計が必要。
4. **デスクトップ最適化（Tauri）による"事務所PCで完結する"体験**
   - 管制・事務は依然PC作業が中心。ブラウザタブに埋もれない常駐デスクトップアプリ、ローカルの軽快さ、印刷/Excel出力との親和性は中小管制の実務にフィットする。

### 3-3. 避けるべき（過剰実装・スコープ膨張のリスク）
- **給与計算・請求書発行の作り込み**: プロキャス/警備フォース等がワンストップで持つが、給与・請求は業務ロジックが重く法対応コストが高い。MVPでは**深追いせず**、集計CSV/Excel出力で会計・給与ソフト連携に留める（本格実装は後続フェーズ）。
- **機械警備・AIカメラ・遠隔監視等のハード連携**: 大手/セコム系の領域。開発検証コストが個人〜小規模開発のキャパを超える。ソフトウェアで完結させる。
- **「AIが全自動で完成シフトを確定」させる過信UX**: 最適化結果を人間の管制員が確認・微修正できる導線（CTSYSも「管制員が確認して反映」の設計）は必須。全自動確定は現場の信頼を損ないやすい。**説明可能性（なぜこの配置か）**を添える。
- **多機能化による日報UXの希薄化**: あれこれ足して「1分日報」の速さを損なうのは本末転倒。軽量入力という核を守る。

## 4. 技術トレンド

### 4-1. Tauri（デスクトップWebViewラップ）の妥当性 → **妥当**
- 2025〜2026年の比較記事では、Tauriは Electron 比で **バイナリサイズ・メモリが大幅に軽い**（実測で150MB→8MB、96%小型化といった報告）とされ、既存の React/Vite フロントをそのまま WebView に載せられる。**MAMOR-AI は React+Vite 資産があるため移行コストが小さく相性が良い**。
- 留意点: TauriはOS標準WebView（Windows: WebView2）を使うため、**レンダリング差異・WebView2ランタイムの配布**を検証する必要（**要確認**）。PC専用MVPで対象を Windows 中心に絞れば検証範囲を限定できる。Rust側の実装は最小限（ファイル保存・印刷・自動更新程度）に留めるのが無難。

### 4-2. AI自動シフト作成の技術動向 → **「数理最適化 × 生成AI」のハイブリッドが主流化**
- WebSearch で確認した業界解説では、シフト作成は **「制約が明確で多岐」なら数理最適化が最適解を即算出**でき、警備のような制約過多の勤務表は**数理最適化が向く**と明言されている。機械学習/LLMは「予測・パターン認識・法令考慮の自動化」に強い。
- 近年は **生成AI（LLM）で現場の曖昧な要望・制約を解釈し、数理最適化ソルバーで割付を解く統合フレームワーク**（生成AI＋数理最適化）を提案する事例が増加。実運用ツールも「AIでシフト自動作成」を謳う製品が17製品以上並ぶ。
- **MAMOR-AI への示唆**: 既存 Claude API は「制約の自然言語入力→構造化」「配置理由の説明生成」「休暇/希望の解釈」に使い、**実際の割付は制約付き最適化（OR-Tools 等のソルバー、または段階的ヒューリスティック）で解く**構成が、精度・コスト・説明性のバランスに優れる。LLM単体に割付を丸投げすると制約違反や再現性の問題が出やすい点は要注意。

### 4-3. Supabase 直結構成の是非 → **MVPでは妥当、ただし責務分離を推奨**
- Supabase（Postgres + Auth + RLS）は既存構成を継承でき、25テーブル設計を活かせる。**RLS でテナント/現場ごとのデータ分離**を設計すれば中小マルチテナントに耐える。
- 留意点:
  - **Claude API キーやシフト最適化ソルバーはクライアント（Tauri/フロント）から直叩きしない**。APIキー露出・課金保護・重い最適化計算のため、既存 Node.js/Express（またはSupabase Edge Functions）をゲートウェイに残す構成が安全（セキュリティは Security Engineer #14 で別途審査）。
  - デスクトップアプリからのSupabase直結は、**RLSが唯一の防御線**になるため設計と検証を先行させる（Database Engineer #08 / Architect と連携）。
- **入力ロジックのUI分離**という指示は、Supabaseスキーマとフロントの間に**ドメイン層（日報バリデーション・シフト制約）を挟む**ことで満たせ、Expo展開時の再利用性も担保できる。

## 5. Plannerへの推奨事項

1. **MVPスコープを「1分日報 × リスク予測連携」に一点集中する**
   既存6モジュールは踏襲しつつ、MVPの目玉は **(a) 1分日報の軽量入力フロー（共通ドメイン層 + Tauryデスクトップ最短導線）** と **(b) 既存Claude APIリスク予測との連携表示**。AIシフト最適化は「差別化の第2弾」として設計は先行しつつ実装優先度は日報の次に置く（理由: 低価格AI配置最適化はCTSYSが先行しており、日報×予測の統合体験の方が独自性が高いため）。

2. **AIシフトは「LLM＋数理最適化ハイブリッド」で、人間の確認前提に設計する**
   割付は制約付き最適化ソルバーで解き、Claude APIは制約の自然言語入力・配置理由の説明生成に用いる。**「AIが下案→管制員が確認・微修正→確定」**の導線と説明可能性を必須要件に。全自動確定は避ける。

3. **価格戦略は"明朗・低価格・スモールスタート"を軸に、上位差別化で単価を守る**
   競合の弱点は「料金非公開・初期費用重い」。MAMOR-AIは **初期費用ゼロ〜低額＋月額の明朗定額（例: 隊員規模別の数千円〜1万円台）** を提示し比較優位を作る。ただしCTSYS（月3,980円〜）とダンピング競争にならないよう、**リスク予測＋1分日報の統合価値で「安いだけでない」ポジション**を維持。具体的な価格帯は Finance/Product Strategist と要調整（**要確認**）。

4. **初期ターゲットは「施設警備（1号）中心の中小警備会社（隊員数十名規模）」に絞る**
   モックアップも施設警備前提で作り込まれており、日報の様式・配置表の粒度が最も合う。交通誘導（2号）は日報項目・配置ロジックが異なるため、MVP後の拡張とする。RYUGENの警備現場実務経験を、日報テンプレート（counter/table/check型）と配置ルールの初期プリセットに反映すると、競合が持たない「現場に馴染む初期設定」で導入摩擦を下げられる。

5. **低ITリテラシー・高齢層を前提にUX基準を設定する**
   警備員の47%が60歳以上。文字サイズ・タップ領域・工程数（1分日報の"最短タップ数"）を明示的なアクセシビリティ要件としてEARS仕様に落とす。将来のExpo（スマホ）展開を見据え、**入力ロジックはUIから分離した共通ドメイン層**として実装する方針を仕様に明記（DesktopとMobileで再利用）。

6. **技術検証（PoC）を実装前に2点先行させる**
   (a) **Tauri + 既存React/Vite + WindowsのWebView2** での動作・印刷・Excel出力・自動更新の検証、(b) **シフト最適化ソルバー（例: OR-Tools）で警備制約（資格・休日・上下番・配置基準）を解けるか**の小規模PoC。いずれもMVPの実現可能性を左右するため Architect (#03相当) / Database Engineer と連携。
