## ADR-001: Webフロントエンドに Next.js を採用し、受付タブレットとWeb管理画面を1つのコードベースで実現

日付: 2026-08-10 / 状態: Accepted

### 背景
受付タブレット（REQ-001〜004）とWeb管理画面（REQ-006〜009）はどちらもブラウザで動作する。個人開発1名でネイティブアプリ2種+Webを別々に持つ工数はない。

### 決定事項
Next.js（App Router）で単一のWebアプリケーションを構築し、`/kiosk/[siteId]`（受付タブレット用ルート、認証不要または拠点固定PIN程度の軽い認証）と`/admin`（管理者用ルート、要ログイン）の2系統のルートを持たせる。UIはTailwind CSS + shadcn/uiを使用（TRAID標準）。

### 代替案
| 案 | 利点 | 却下理由 |
|----|------|---------|
| 受付タブレット専用の別リポジトリ・別技術（Electron等） | 常設端末向けに最適化しやすい | 個人開発でメンテナンス対象が増える。ブラウザで十分要件を満たせるため過剰設計（YAGNI） |
| 静的サイト（SPA）+ 別バックエンドAPI | フロントとバックの分離が明確 | Next.jsのServer Actions/Route Handlersで十分にAPI層を賄えるため、別立てにするメリットが薄い |

### スケーラビリティ評価
- 100拠点/1,000拠点/10,000拠点: Next.jsのVercelデプロイは静的資産中心のため拠点数の増加自体はスケール要因にならない。ボトルネックはバックエンド側（ADR-003参照）

### 結果
Frontend Developer(#12)は`/kiosk`と`/admin`をNext.js内の別ルートグループとして実装する。

## ADR-002: モバイルアプリは Expo (React Native) を採用

日付: 2026-08-10 / 状態: Accepted

### 背景
REQ-010（現在滞在者一覧のリアルタイム表示）、REQ-011（退場忘れアラート通知）を警備員・管理者が携行するスマホで実現する必要がある。

### 決定事項
Expo (React Native) を採用する。プッシュ通知は`expo-notifications`を利用する。

**注記:** 姉妹プロジェクト「警備員検定・資格試験対策アプリ」はRYUGENの指示でExpoからネイティブiOS(Swift/SwiftUI)へ方針変更(ADR-005)した経緯があるが、本プロジェクトは開発初期段階であり、RYUGENから同様の指示がない限りExpoを既定路線とする。もし将来「入退管理システムもXcode/ターミナルでネイティブ開発したい」という指示があれば、姉妹プロジェクトのADR-005と同様の見直しを行う想定とする。

### 代替案
| 案 | 利点 | 却下理由 |
|----|------|---------|
| ネイティブiOS/Android別々 | 各OS最大性能 | 個人開発1名でAndroid/iOS両対応する工数がなく、本プロジェクトはAndroid端末を使う中小事業者（現場の安価なAndroidタブレット/スマホ運用が多い）も取り込みたいためクロスプラットフォームが必須 |
| PWA（Webのみ、ネイティブアプリなし） | 実装コストが最小 | プッシュ通知（REQ-011のアラート）の信頼性がネイティブアプリに劣り、警備員が「気づかない」リスクが高い。現場での即応性が製品価値の核なので妥協できない |

### スケーラビリティ評価
- クライアント側の負荷は拠点数に依存せず、ボトルネックにならない

### 結果
Frontend Developer(#12)はExpo SDK最新版でモバイルアプリを実装する。

## ADR-003: バックエンドに Supabase（警備員検定アプリとは別プロジェクト）を採用

日付: 2026-08-10 / 状態: Accepted

### 背景
REQ-005〜007（拠点・権限管理）、REQ-014（追記型ログ）を1名運用で構築・保守する必要がある。姉妹プロジェクトと同じSupabaseを使うが、データ分離のため別プロジェクトとする。

### 決定事項
新規のSupabaseプロジェクトを作成し、Postgres + Auth + Realtime + RLSを使用する。REQ-010/011のリアルタイム性はSupabase Realtime（Postgres Changes購読）で実現する。

### 代替案
| 案 | 利点 | 却下理由 |
|----|------|---------|
| 警備員検定アプリと同一Supabaseプロジェクトを共用 | インフラコストの節約 | 全く異なる顧客・データ（入退管理は企業の来訪者個人情報を扱う）を混在させるのはセキュリティ・監査の観点で不適切。trend-research-report.mdの推奨にも反する |
| Firebase (Firestore + Realtime Database) | リアルタイム機能が手厚い | RLS相当のきめ細かい行レベルセキュリティ（REQ-007の拠点別アクセス制御）がFirestore Security Rulesでは監査・テストがしづらい。SQLベースの検索・集計（REQ-008）もPostgresが得意 |
| 自前サーバー + WebSocket自前実装 | 完全な自由度 | 個人開発1名でリアルタイム基盤の運用まで担うのは$45/月目標・保守コストの両面で非現実的 |

### スケーラビリティ評価
- 100拠点: Supabase Freeプランで十分
- 1,000拠点: Supabase Proプラン($25/月)で十分。Realtimeの同時接続数（拠点ごとに警備員複数名が購読）を監視する必要あり
- 10,000拠点: Pro継続または従量課金追加。Realtime接続数がボトルネックになりやすいため、この規模に達したら拠点単位でのチャンネル設計最適化が必要（finance-agentへコスト再評価依頼）

### 結果
Database Engineer(#08)はSupabase Postgres + RLS + Realtimeを前提にスキーマ設計を行う。

## ADR-004: 退場忘れアラート(REQ-011)はSupabase Edge Function + pg_cron による定期チェック方式を採用

日付: 2026-08-10 / 状態: Accepted

### 背景
REQ-011は「滞在時間が閾値を超えたら通知」というポーリング型の判定が必要。Realtime購読だけでは「時間経過」というイベントを検知できない。

### 決定事項
Supabase の pg_cron 拡張で数分間隔（例: 5分ごと）にEdge Functionを起動し、入場中(退場時刻null)かつ滞在時間が拠点別閾値(REQ-012)を超えたレコードを抽出、該当拠点の警備員・管理者へExpo Push Notificationを送信する。

### 代替案
| 案 | 利点 | 却下理由 |
|----|------|---------|
| クライアント側（モバイルアプリ）でタイマー監視 | サーバー実装が不要 | アプリがバックグラウンドや未起動の場合に検知できず、REQ-011の「気づく」という目的を果たせない |
| Realtimeのみで即時通知 | リアルタイム性が高い | 「時間経過」自体はイベントではないため、Realtime単体では実現不可。定期チェックの仕組みが別途必要 |

### スケーラビリティ評価
- 100〜10,000拠点: pg_cronのクエリは「入場中レコードのみ」を対象にするため、拠点数が増えても入場中レコード数（同時滞在者数、通常は数十〜数百件程度）に比例するのみでスケールしやすい

### 結果
Database Engineer(#08)は`visit`/`vehicleVisit`テーブルに「入場中判定用の部分インデックス（退場時刻がnullの行のみ）」を設計する。

## ADR-005: 認証・権限モデルは Supabase Auth + 拠点別ロール(site_roles)テーブルで実装

日付: 2026-08-10 / 状態: Accepted

### 背景
REQ-007（拠点別権限管理）はHighリスク要件。担当外拠点のデータ漏洩を防ぐ設計が必須。

### 決定事項
Supabase Authでユーザー認証を行い、`site_roles`テーブル（user_id, site_id, role）で「どのユーザーがどの拠点に対してどの権限（admin/guard）を持つか」を管理する。RLSポリシーは全ての入退記録系テーブルで「`site_roles`に自分のuser_idとレコードのsite_idの組み合わせが存在するか」をチェックする形にする。

### 代替案
| 案 | 利点 | 却下理由 |
|----|------|---------|
| ユーザーごとに単一ロールのみ（拠点跨ぎなし） | シンプル | 1人の警備員が複数拠点を巡回する実務（RYUGENの実務経験）に合わない |
| アプリケーション層のみでアクセス制御（RLSなし） | 実装がシンプルに見える | バグ1つで全拠点のデータが見えてしまうリスクがあり、REQ-007のHighリスク評価に見合わない。RLSでDB層からも二重に守る設計が必須 |

### スケーラビリティ評価
- 100〜10,000ユーザー: `site_roles`はuser_id×site_idの組み合わせのみを持つ軽量テーブルであり、適切なインデックス（user_id, site_id複合）でスケールする

### 結果
Database Engineer(#08)は`site_roles`テーブルを中心にRLSポリシーを設計する（詳細は本ドキュメント末尾の申し送り参照）。

## Database Engineer への申し送り事項（RLS設計の先行方針）

1. **`site_roles`テーブル**: `(user_id, site_id, role)`。RLSは自分自身の行のみSELECT可能とし、INSERT/UPDATE/DELETEは`role='admin'`を持つユーザーのみ許可する。ここが破られると全拠点権限モデルが崩壊するため、最優先でクロスユーザーRLSテストを書くこと（REQ-007）。
2. **`visit`テーブル・`vehicle_visit`テーブル**: 全レコードに`site_id`必須（REQ-005）。RLSは「`site_roles`に`auth.uid()`と当該`site_id`の組み合わせが存在する」ユーザーのみSELECT/INSERT可能とする。**UPDATE/DELETEポリシーは一切定義しない**（REQ-014の追記型ログ・改ざん防止。訂正は取消レコードのINSERTのみで表現する）。
3. **退場忘れアラート用インデックス**: `visit`/`vehicle_visit`テーブルに`exited_at IS NULL`の行のみを対象とした部分インデックス(partial index)を作成し、ADR-004のpg_cronクエリのパフォーマンスを担保する。
4. **個人情報の保持期間管理（REQ-015）**: `sites`テーブルに`data_retention_days`列を持たせ、pg_cronの別ジョブで保持期間超過レコードの氏名・連絡先列をマスキングする設計とする（レコード自体の削除ではなく機微情報のみのマスキングとし、入退記録の存在自体はREQ-014の監査要件のため残す）。
5. 全テーブルで「担当外site_idへのクロスアクセス試行が拒否されること」をSQLレベルのテストで検証すること（behavioral-spec.md REQ-007のテスト可能性に対応）。
