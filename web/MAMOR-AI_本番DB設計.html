PRODUCTION DB & ONBOARDING DESIGN

MAMOR-AI 本番DB設計・オンボーディング

Supabase実DBへの本番運用結線の設計。マルチテナント（運営→会社→現場→勤務員）のオンボーディング、 認証・RLSモデル、アカウント発行、テーブル設計、移行手順をまとめる。移行SQL 0400_production_onboarding.sql は実Postgresで適用・検証済み。

対象: mamorai.tryangrow.comDB: Supabase(PostgreSQL)版: v1.0 設計2026-08

01方針（マルチテナント）

運営(TRYANGROW)は「会社」を発行し、会社は自社の「現場」と「勤務員」を作成する。運営は現場業務を持たず、 会社・契約の管理に徹する。これにより複数会社への拡大に耐える多テナント構成とする。

主体入口発行・作成するもの

会社/co現場（施設コード＋現場PIN）／勤務員（スタッフNo＋PIN）／講習会・労務ルール

02オンボーディング・フロー

運営は「会社と会社管理者」までを発行する。以降の現場・勤務員は各会社が自分で作成する（自走）。 初回のブルガリ立ち上げは、運営が会社→現場→勤務員まで一括発行して素早く開始し、以降は会社に委譲してよい。

03認証・RLSモデル（二系統）

会社・運営はSupabase Authでログインし、auth.uid()に基づくRLSで自社/全体のデータのみに絞られる。 現場（共有端末）・勤務員（スマホ）はAuthユーザーを持たず、コード＋PIN照合のログインRPCでセッションを発行し、 業務の読み書きはSECURITY DEFINERの専用RPC（次段0401）で会社・現場スコープを内部強制する。

検証済み。 本設計の 0400 を実PostgreSQLに適用し、①会社発行→会社管理者紐付け→現場作成(PIN発行)→勤務員登録→勤務員ログイン(正PIN成功/誤PIN拒否) の全チェーン、②RLSで自社データのみ可視・別会社は0件（テナント分離） を確認した。

04アカウント発行の手順とセキュリティ

発行対象方法秘密情報の扱い
会社（識別コード）運営が platform_create_company(name, code)—（公開コード）
会社管理者アカウントサーバ(service_role)でAuthユーザー作成 → platform_link_company_admin(user_id, company_id) でロール付与service_roleはサーバ環境変数のみ。クライアントに置かない
現場（施設コード＋PIN）会社が company_create_site(name, code, dept, pin)PINは pgcrypto(bf) でハッシュ保存。平文は保持しない
勤務員（スタッフNo＋PIN）会社/現場が company_register_staff(no, name, dob, dept, role, site_ids, pin)PINはハッシュ保存。担当現場は staff_sites で複数可

service_role について。 会社管理者の作成（Authユーザー発行）だけは管理者権限が必要なため、 クライアントのpublishable keyでは行わない。server(Express)にservice_roleを置いた発行用エンドポイント、 または当面はSupabaseダッシュボードでの手動作成＋platform_link_company_admin で対応する。

06アプリ内ストア → テーブル 対応（移行）

現在アプリはブラウザのlocalStorageで動作している。本番化では各ストアを下表のテーブルへ結線する（次段0401でフロント実装）。

現在のストア(localStorage)移行先テーブル
leaveStore（有給）leave_requests
shiftHopeStore（シフト希望）shift_hopes
shiftStore（月次シフト）shift_snapshots
trainingStore（講習会）seminars / training_apps
staffStore（勤務員登録）staff / staff_sites
reportImportStore（日報取込）report_months / report_incidents

同一ブラウザ内でしか共有されない現状の制約が、DB結線後は勤務員のスマホ・現場PC・会社PC間でリアルタイム反映され、 恒久保存・バックアップ・権限分離（RLS）が実現する。

07移行・ロールアウト手順

  1. DB適用：Supabase SQL Editor で 0400_production_onboarding.sql を実行（冪等・追加のみ）。
  2. 運営で会社発行：運営が ヒトトヒト株式会社（HTH-0001）を発行。会社管理者Authユーザーをサーバ/ダッシュボードで作成し紐付け。
  3. 会社で現場・勤務員作成：会社が ブルガリホテル東京（BVL-01）を作成（現場PIN発行）、勤務員6名を登録（スタッフNo＋PIN）。
  4. フロント結線(0401)：現場/勤務員の業務RPC（submit/list/approve）を追加し、各画面をSupabaseへバインド。localStorageストアをテーブルへ置換。
  5. 検証・切替：端末間反映・RLS分離・帳票出力を本番データで確認し、デモ(localStorage)から本番へ切替。
